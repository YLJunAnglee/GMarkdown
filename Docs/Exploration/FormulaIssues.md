# 公式问题：原因、方案与结果

## F-007：TextView 混合段落中的双美元公式被强制换行（2026-09-17，通过）

**样本：**《高中物理必备知识》第 65 章“核反应相关知识点”的第 2 个 TXT 块。原始内容含 `设放射性元素$${}_{Z}^{A}\text{X}$$经过`，双美元公式嵌在二级标题同一行的连续文字中。

**运行证据：**用户截图确认分块路径保持行内；TextView 路径却为每个该类公式创建独立居中行，破坏文字连续性。后续表格中 `\begin{aligned}` 源码泄漏经原始内容核对为单 `$` 开始、`$$` 结束的源数据定界符不配对，不属于本问题且不改写数据。

**修改：**TextView 的公式附件模式现在依据 AST 上下文决定：仅完整的公式段落使用块级附件；标题、粗体及混合段落内的 `$$...$$` 使用行内附件。表格单元格维持现有显示公式处理。新增 `FormulaModeTests.testTextViewKeepsDisplayDelimitersInlineOutsideStandaloneParagraphs` 覆盖标题、粗体、独立段落的模式选择。

**验证结果：**用户重新运行后的 TextView 截图确认首个核素公式回到“设放射性元素”与“经过”之间的连续行内流；先前分块截图在同一位置也正确。两条路径通过。`git diff --check` 已通过；助手未编译或运行测试。

## F-008：不配对 `aligned` 定界符的受控降级（2026-09-17，通过）

**样本：**同一章第 3 个 TABLE。“人工转变”原文为 `$\\begin{aligned}…\\end{aligned}$$`，即开头一个 `$`、结尾两个 `$`；其后“重核裂变”行使用完整的 `$\\begin{aligned}…\\end{aligned}$`。

**原因：**既有非贪婪单美元匹配会以双美元结尾的第一个 `$` 收束第一式，留下第二个 `$` 与下一行的开头 `$` 配对，从而将中间表格结构吞入公式范围。`\\begin` 因此作为普通源码泄漏。

**修改：**仅对这个确定的 `aligned` 失配形式，且双美元后紧跟表格/Markdown 边界（`|`、空白、换行或结束）时，在预处理的派生文本中将开头补成 `$$`；原始 JSONL 和“原始内容”不变。普通文本、任意不闭合 `$`、其它环境均不作猜测性补全。新增 AST 测试验证两条公式和两行表格均独立保留，并验证相邻 `$...$` 公式不会被恢复规则吞连。

**验证结果：**用户重新运行后的分块与 TextView 截图均无 `\\begin` 源码泄漏；人工转变、重核裂变、轻核聚变公式分别可见，表格行未合并。两条路径通过。`git diff --check` 已通过；助手未编译或运行测试。

## F-006：化学公式扩展命令显示为红色源码（2026-09-14）

**样本：**《高中化学反应方程式汇总.pdf》`book-9BBC4A5C-D4C2-4A79-A062-EA8A9D614D8C.jsonl`，第 7 章“硫及其化合物性质”。原始 `txt` 的化学式使用 `\\ce{…}`，反应条件使用 `\\xlongequal{…}`。用户截图中，分块渲染把这两个命令显示为红色文字，命令后的参数却被当作普通数学内容继续排版。

**原因：**SVG 公式转换器原先只装载手工列出的 MathJax 包，未包含 `mhchem` 与 `extpfeil`。`\\ce` 属于 `mhchem`，`\\xlongequal` 属于 `extpfeil`；项目同时启用了 `noundefined`，故未知命令不会使整条公式失败，而是以红色源码显示。原始书籍数据无须也不应改写。

**修改：**公式转换器改用 MathJaxSwift 的 `TeXInputProcessorOptions.Packages.all`。该包集包含上述扩展，保留原公式字符串和既有 `noundefined` 降级行为，用于仍不受支持的其他命令。

**验证结果（2026-09-14，用户运行）：**用户重新运行该章节后确认红色源码已消失，真实章节的 `\\ce` 与 `\\xlongequal` 兼容问题通过。截图所示为分块渲染；TextView 路径尚未单独记录。助手未编译、未运行 Swift 测试或 Demo。

记录日期：2026-09-09。基线及数据来源见 [探索记录](README.md)。

## F-001：集合花括号丢失

状态：分块最小样本 11/12 已通过；Package 测试、TextView、表格和真实章节回归待验证。

### 证据

对照项 11：`$$P(\{e_i\})$$`。

- 原始公式体：`P(\{e_i\})`；直接交给 SwiftMath 和 SVG 路径，用户截图均有集合花括号。
- 经过 GMarkParser + GMarkupStringifier 后：`P({e_i})`。
- 日志：`nodes=1, blockHandlerMatches=1, payloadUnchanged=false`。
- 解析后的输入分别交给两个后端，截图均变为没有集合花括号的 `P(e_i)`。

结论：该样本的花括号缺失不是后端不支持。用于显示花括号的反斜杠在解析传递过程中消失，普通花括号随后被 LaTeX 当成分组符。具体修复需检查预处理与 AST 传输方式，不应归责为 stringifier 单独删除反斜杠。

相关源码：

- [GMarkPreprocessor.swift](../../Sources/Parser/Preprocessor/GMarkPreprocessor.swift)：以 `<LaTex>` 包裹公式后仍交给 Markdown 解析。
- [GMarkupStringifier.swift](../../Sources/Visitor/GMarkupStringifier.swift)：从解析节点重建文本。
- [LaTexMarkupHandler.swift](../../Sources/Generator/MarkupHandler/LaTexMarkupHandler.swift)：识别段落并调用公式后端。

### 拟修改方案

在 Markdown 解析前保护完整公式内容，在公式渲染边界恢复原文，使反斜杠、下划线、星号、花括号等不被 Markdown 解释。具体采用占位符、转义传输或其他机制，需先以最小实验验证；当前未选定实现。代码块中的类似公式文本必须维持代码语义。

不采用“在解析后猜测补回反斜杠”的修补方式。

### 验收

- 对照 11 必须保留可见花括号；对照 12 `P({e_i})` 必须继续保持只有分组、无可见花括号。
- 后端收到的公式体与预期原文一致，明确允许的变化仅为剥离外层公式定界符。
- 继续检查下划线、星号、相邻公式、行内/块级公式以及表格中的公式。
- 第 20 章真实公式中的集合括号恢复；不能因此宣称中文和编号已解决。

## 2026-09-09 · F-005：核对行内/块级语义

预期约定：`$公式$` 为行内，`$$公式$$` 为独立公式块。用户所说两个/四个美元符号指左右合计数量。本次核对当前 GMarkdown 探索仓库，不据此推断旧业务项目全部历史实现。

源码结论：当前链路没有完整落实该约定。

1. `LaTeXPreprocessor` 匹配两种定界符，但均包装为相同 `<LaTex>`。定界符仍保留在编码后的 payload 内，并非识别阶段已不可恢复；然而没有形成明确的行内/块级类型，也没有按双美元建立独立块边界。
2. `LaTexMarkupHandler.canHandle` 根据段落首尾是否是 LaTex 标签认定公式块，不检查美元数量。因此独立段落中的 `$x^2$` 也会走公式块路径，正文内的 `$$x^2$$` 不会仅因双美元就被拆成独立块。
3. TextView 的 `DefaultInlineHTMLPlugin` 对两种输入创建相同 `MDLaTexAttachedProvider`，没有传入公式类型。F-004 新增的滚动容器因此适用于所有公式：短公式不滚动，超宽行内公式也会滚动。它没有主动将所有公式独占一行，但也没有实现“仅块级公式使用横向滚动”的区分。
4. `GMarkLaTexRender.trimBrackets` 剥离单/双美元后渲染，`GMarkLaTexToSVGConverter` 实际使用的 conversionOptions 固定 `display: true`，图片缓存也未区分行内/块级模式。即使外部文字位置像行内，后端公式排版模式仍未据定界符切换。
5. 对照 HEAD 的原始预处理实现，也使用统一标签，并按长度大于 30 或包含换行添加换行，未按定界符严格区分。F-001 移除了这一长度启发式，但没有补齐公式类型；此次明确记录该缺口。

## T-004：宽表缺少横向浏览提示（2026-09-14）

**样本：**《（超详）高中数学知识点归纳汇总.doc》`book-68F2580E-9309-4FC7-8CFA-1620E764F8CD.jsonl`，第 3 章“高中数学必修1知识点”，第 2 个原始块，标题“[1.1.2] 集合间的基本关系（6）子集、真子集、集合相等”。

**原始数据对照：**该 TABLE 明确有 5 列：名称、记号、意义、性质、示意图。用户截图的左、中、右内容分别是同一张表在横向滚动后的不同视区，不是解析生成的三张表；表格的列数和行数未丢失。

**原因：**`GMarkTableView` 以内部横向 `UIScrollView` 保留超宽列；此前显式关闭了横向滚动条并禁用回弹，窄屏初始只露出约 3 列，且没有任何可发现性提示，因此视觉上像表格被截断或拆分。

**修改：**`GMarkTableView` 已开启横向滚动条、横向回弹和方向锁定；内容宽于视区时首次布局闪现滚动条。表格重用/刷新时也会复位至最左列，避免新表继承上一张表的横向位置。不会压缩列宽或改写表格、公式及原书数据。

**输入核对：**该原始块的两个“或 B ⊇ A”“或 B ⊋ A”公式的美元定界符实际成对；右括号位于数学定界符内。这不是跨单元格吞噬内容的证据，原书数据未改动。

**待用户验证：**重新打开该章节的分块渲染和 TextView 渲染，确认宽表首次出现横向提示，左右拖动可连续查看 5 列，且纵向页面滚动不受影响。尚未编译或运行。

## T-006：表格单元格两行截断（2026-09-14）

**复现与证据：**《（超详）高中数学知识点归纳汇总.doc》`book-68F2580E-9309-4FC7-8CFA-1620E764F8CD.jsonl`，第 3 章“高中数学必修1知识点”，第 2 个 TABLE 块。用户提供的原始内容截图显示该表有 5 列；“子集”行的“性质”单元格含 4 条、其“示意图”单元格含两个由 `\\boxed`/`matrix` 表达的示意图。横向查看截图中，名称、记号、意义列与原始块相符，但“性质”只显示第 1 条，示意图仅见“或”，其余源内容未显示。此问题发生在表格单元格内部，不是不同横向视区造成的列缺失。

**原因：**`DefaultTableStyle.maximumNumberOfLines` 固定为 `2`；`GMarkTableLayout` 将它传给 `MPITextRenderer`，分块和 TextView 的表格路径均使用该布局。因此含 `<br>` 的长单元格和复杂公式被限制为两行，行高也只能按被截断后的 renderer 计算。

**修改：**将默认表格单元格最大行数设为 `0`（MPITextKit 的不限行值），保留自然列宽、横向滚动和原始书籍内容，不对数据做清洗或截断。

**待验证：**用户重新打开同一章节的“分块渲染”和“TextView 渲染”，向右查看“性质 / 示意图”两列。预期“子集”行完整显示 4 条性质及两个方框示意；“真子集”行完整显示 2 条性质及一个嵌套方框；“集合相等”行完整显示 2 条性质和 `A(B)` 方框。未编译、未运行 Swift 测试或 Demo。

**验证结果（2026-09-14，用户运行）：**iPhone 17 模拟器、iOS 26.3 的“分块渲染”和“TextView 渲染”截图均与第 2 个原始 TABLE 块逐格核对通过。名称（子集 / 真子集 / 集合相等）、记号、意义、性质和示意图均与原始 `txt` 对应；其中子集行的 4 条性质、真子集行的 2 条性质、集合相等行的 2 条性质，以及两个子集方框图、真子集嵌套方框图和 `A(B)` 方框图均可见。两条路径均无两行截断或公式图缺失。助手未编译、未运行 Swift 测试或 Demo。

**样本：**《高中数学必修+选修知识点总结 .pdf》`book-7B333026-A9BD-4FC5-8A4A-53885E3BAA52.jsonl`，第 11 章“函数单调性知识点”，第 2 个 TABLE 块。原始“图像”单元格含带 `src`、`width`、`height` 与 `alt` 的 HTML `<img>`；用户分块渲染截图显示该列为空，定义与判定方法列均与原始 `txt` 相符。

**原因：**swift-markdown 将表格内原始 `<img>` 表示为 `InlineHTML`，`GMarkupVisitor` 原先仅特别处理 `<br>` 等标签，不会将 `src` 交给 `ImageLoader`，结果为空富文本。TextView 的默认表格插件另有未传递 `imageLoader` 给 `GMarkupTableVisitor` 的遗漏。

**修改：**`GMarkupVisitor` 现识别带引号 `src` 的 `<img>` 并按 Markdown 图片创建附件；默认表格插件将外层 `imageLoader` 传给表格访问器。原始图片 URL 和数据不改写。

**验证结果（2026-09-14，用户运行）：**分块渲染的“图像”列出现灰色图片附件，证明 HTML 图片已被解析并交给加载器，不再是解析遗漏造成的空单元格。原始 `src` 使用 `via.placeholder.com`；该占位图片服务已停止提供图片，因而没有可显示的位图。按“展示忠实对应导出数据”的标准，HTML 图片引用已保留并触发加载；实际图片不可得属于外部源资源不可用。TextView 路径仍待验证。助手未编译、未运行 Swift 测试或 Demo。

**降级策略修改：**不使用第三方公共占位图 API（其默认字体无法可靠显示中文）。HTML 图片保留原始 `src` 进行首次加载；Nuke 加载失败时，Demo 在原图片区域用系统字体居中、多行显示原始 `alt`。`ImageLoader` 新增有默认实现的 `fallbackText` 重载，现有接入方保持原行为；分块与 TextView 的表格路径都能传入该 `alt`。用户首次验证已确认分块路径显示“递增函数图像”。

**样式调整（2026-09-14）：**用户要求表格采用安卓端的细线网格风格，且失败图片仅显示文本。因此默认表格现改为 1pt `#D1D5DB` 网格线、直角、浅灰表头 `#F3F4F6` 与白色正文；表头、正文、交替行和边线颜色都集中在 `DefaultTableStyle`，可直接替换。分块与 TextView 共用该配色与网格设置。图片加载过程中不再使用灰色 placeholder；加载失败的 `alt` 标签背景为透明，仅保留文字。用户已确认当前表格样式无问题。助手未编译、未运行 Swift 测试或 Demo；图片降级的两条路径仍应在后续样本中分别记录。

**替代方案评估：**用户提供的 AIEndorser `FormulaImageService.domesticURL(formula:)` 实际位于其 `StringRichExtension.swift`，用于将 LaTeX 公式请求编码并转发到该项目配置的私有 `/latex/latexToSvg.do` 服务。它不是通用图片代理，且当前 `<img>` 表示“递增函数图像”而非可替换为 LaTeX 的公式；不接入 GMarkdown，以免将外部图片失败伪装为公式或引入另一项目的配置依赖。

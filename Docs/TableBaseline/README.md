# GMarkdown TABLE 原库基线

## 基线范围

- 日期：2026-08-24
- GMarkdown 生产源码基线：`c235d3a8d884f8da308236f84a894421287ef3c9`
- 测试分支：`feature/native-table-rendering`
- 设备：iPhone 16 Pro 模拟器，iOS 18.6
- 构建：Debug，容器宽度 370 pt
- 渲染链路：`GMarkProcessor -> GMarkParser -> GMarkChunkGenerator -> GMarkdownMultiView`

本步骤只在 Example 中增加基线入口、指标展示和截图参数，没有修改 `Sources` 下的生产解析、布局或渲染代码。Example 中的 A、B、C 资源已通过 `cmp` 与解析测试 Fixture 逐字校验一致。

## 正确表现

- 样例 A 的 `\cdots` 已渲染为公式结果，没有显示美元符号或 LaTeX 源码。
- 样例 B 保留空表头单元格，表格仍为 4 列、2 行数据。
- 样例 C 的短公式和中英文混排可以显示。
- `<br>` 产生两行内容并增加对应行高。
- 转义竖线 `\|` 显示为单元格内的 `|`，没有错误拆列。
- 列数不齐的输入可以继续渲染；解析测试已确认缺列补空、多列截断。
- 样例 C 从顶部定位到底部后，长公式表和列数不齐表仍显示对应内容，未观察到明显的上一块内容残留；这只作为 Example 内部 UICollectionView 复用基线，不替代 AIEndorser 业务 Cell 的复用验证。

## 已确认问题

1. 长度超过 30 个字符的 LaTeX 被预处理器插入换行。原始长公式数据行被拆成三行：第一行只显示“长公式”，第二行只显示公式，第三行只显示备注；该表的原始 2 行数据最终变为 4 行。
2. 样例 A 的 5 列总宽度超过 370 pt，初始视口只显示前 4 列，需要横向滚动才能看到“积分”列。
3. 样例 B 内容较短时表格没有填满容器宽度，右侧留下较大空白。
4. 长中文、无断点英文和多行内容受到当前列宽及默认最多两行样式限制，存在不自然换行或裁切风险。
5. 自动把表格内部滚动视图定位到最右侧后，能够显示“积分”列，但截图中页面上方部分文字出现异常缺失。该现象需要用真实手势复核后，才能判断是表格滚动实现问题还是基线工具直接设置内部偏移造成的差异。

## 阶段结论

原库可以稳定展示普通短表格、空表头和短行内公式，且固定样例未观察到首次布局后的高度跳变；但长公式预处理会直接破坏 TABLE 行结构，因此不能在现状下接入业务。第 4 步应只修复 TABLE 内 LaTeX 预处理和解析，并用现有测试及本基线做修改后对照。列宽、最多两行、短表不铺满和滚动细节留到后续布局步骤处理。
